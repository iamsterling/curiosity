# Mem0 OSS reverse-engineering dossier

**Date:** 2026-08-26

**Status:** bounded clean-room source study complete

**Disposition:** architecture input only; no implementation, production use, or
authority transfer is authorized by this record

## Executive finding

**Documented.** Mem0 OSS at the inspected revision is an application-memory
library, not an evidence or lifecycle authority. Its Python and TypeScript OSS
paths extract additive natural-language memories, store embeddings and payloads
in a configurable vector database, keep mutation history and a rolling message
window in a separate history store, and maintain a second vector collection of
heuristically extracted entities. Python package metadata reports `2.0.19`, the
TypeScript package reports `3.1.7`, and both default their response/config
version to `v1.1`. [PY-PACKAGE] [TS-PACKAGE] [PY-CONFIG] [TS-CONFIG]

**Inference.** The reusable architectural lesson is the separation of additive
extraction, semantic/keyword/entity retrieval signals, and optional history.
The implementation is not safe to transplant as Curiosity's canonical memory,
Ledger, authorization, or evidence substrate. The stores have no shared
transaction, the scope identifiers are caller-selected filters rather than
authorization decisions, provenance is too weak for evidence use, and several
best-effort paths can leave cross-store drift while still returning success.

**NO-GO.** Do not compose Mem0 into the private runtime, publish or deploy it,
copy its extraction prompt or implementation, treat its scores as confidence,
or dual-write its records with plugin Ledger state under the authority of this
research record. Any implementation or production experiment requires a
separate reviewed decision and must preserve the repository constitution's
Ledger, EventCapture, release, and deployment boundaries.

## Question and boundary

1. What observable local behavior could an independent implementation
   reconstruct from Mem0's public source?
2. Where do Python OSS, TypeScript OSS, the self-hosted server, and hosted

3. Which failure, authorization, telemetry, migration, and data-lifecycle
   properties make the design unsuitable as an authority without containment?

## Architecture and data ownership

### Local OSS stores

| Store                            | Python OSS contents                                                                                                                  | TypeScript OSS contents                                                                                | Authority observation                                                                                                                                                              |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary vector collection        | UUID, embedding, memory text in `data`, exact-text MD5, lemmatized text, timestamps, scope IDs, attribution, expiry, caller metadata | Same concepts, but several payload names are camelCase (`createdAt`, `textLemmatized`, `attributedTo`) | Primary live memory; adapter-specific consistency and filter semantics [PY-ADD-PERSIST] [TS-ADD-PERSIST]                                                                           |
| Entity vector collection         | Extracted entity text/type, scope IDs, `linked_memory_ids`                                                                           | Extracted entity text/type, scope IDs, `linkedMemoryIds`                                               | Rebuildable ranking projection, not an external graph or relationship authority [PY-ENTITY-WRITE] [TS-ENTITY-WRITE]                                                                |
| History database                 | SQLite `history` and `messages` tables                                                                                               | Default SQLite `memory_history` and `messages`; alternative history managers exist                     | Mutation log and extraction context, but not transactional with either vector collection [PY-SQLITE] [TS-SQLITE]                                                                   |
| Self-hosted application Postgres | Users, API-key hashes, request logs, refresh JTIs, settings; pgvector memory collection is separately managed by the vector adapter  | Not applicable                                                                                         | Authentication/configuration and vector persistence share a server deployment, not one transaction or schema authority [SERVER-MODELS] [SERVER-ALEMBIC-AUTH] [SERVER-ALEMBIC-LOGS] |

**Documented.** Python constructs the embedder, primary vector store, LLM, and
SQLite manager independently. It creates the entity store lazily as a separately
named collection. [PY-INIT]

**Inference.** There is no single canonical record from which every other store
can be deterministically accepted as current. The vector payload is treated as
the live memory, SQLite as history, and the entity collection as a ranking
projection, but no persisted generation, commit ID, outbox, or reconciliation
cursor binds them.

### Primary schemas

**Documented.** Python's public `MemoryItem` has required `id` and `memory`, plus
optional `hash`, metadata, score, and timestamps. Scope IDs, role, actor,
attribution, and expiry are promoted dynamically outside that declared model.
[PY-CONFIG] [PY-GET]

**Documented.** TypeScript declares camelCase timestamps and attribution but
stores scope IDs in snake_case. Its raw `infer: false` result places `event:
"ADD"` inside `metadata`, whereas Python returns `event` at the result's top
level. [TS-TYPES] [TS-ADD]

**Documented.** Python history rows contain a random history-row ID, memory ID,
old/new text, event, created/updated times, deletion flag, actor ID, and role.
TypeScript's default SQLite history omits actor and role and returns rows newest
first by autoincrement ID; Python orders by created and updated time ascending.
[PY-SQLITE] [TS-SQLITE]

**Inference.** A language-neutral consumer cannot safely share a collection or
history database without an explicit normalization layer. The migration guide
itself warns that Python's `text_lemmatized` and TypeScript's `textLemmatized`
break cross-language lemma/BM25 behavior. [MIGRATION]

## Exact operation traces

### Add with inference: Python sync

**Documented trace.** [PY-ADD] [PY-ADD-PERSIST] [PY-ENTITY-WRITE]

```text
add(messages, at least one scope ID, metadata, infer=True)
  -> reject OSS-only temporal timestamp; normalize expiration_date
  -> strip identity keys from caller metadata
  -> normalize messages and optional vision content
  -> load last 10 messages for the escaped scope key from SQLite
  -> embed the current role-labelled messages for search
  -> retrieve at most 10 semantically similar memories in that scope
  -> expose those memories to one additive-extraction LLM call
  -> provider failure: raise LLMError with the provider error as cause
  -> empty or malformed response: save source messages, return no memories
  -> batch-embed extracted texts; fall back to individual embedding
  -> exact MD5 dedup against only the 10 retrieved memories and this batch
  -> prepare UUID/payload records
  -> batch insert primary vectors; on failure, retry each record and log failures
  -> write ADD history for every prepared record; fall back row by row
  -> heuristically extract and upsert entities into a second collection
  -> save the rolling source-message window
  -> emit sampled telemetry and return every prepared record as event ADD
```

**Documented.** The extraction system prompt declares ADD as its sole operation.
Existing memories are presented only for deduplication and linking. The migration
guide independently describes one LLM call with no inferred UPDATE or DELETE.
[PY-PROMPT] [MIGRATION]

**Contradiction.** The `add()` docstring still says inference decides whether to
add, update, or delete related memories, while the runtime and migration guide
are ADD-only. Consumers should trust the executed path, not that stale sentence.
[PY-ADD] [MIGRATION]

**Documented.** Deduplication is exact MD5 over the extracted text. The comparison
set is not the whole scope: it consists only of hashes present in the ten semantic
context hits plus hashes already prepared in the current call. [PY-ADD-PERSIST]

**Inference.** Exact duplicates outside those ten context hits can be inserted.
Semantically equivalent paraphrases can also be inserted unless the LLM elects
to suppress them. Concurrent calls can both search before either inserts, so the
algorithm provides neither global uniqueness nor idempotency.

**Documented high-risk failure.** After a failed batch insert, individual insert
failures are logged but removed from neither `records` nor the subsequent history
batch nor the returned result. The caller can therefore receive an ADD result and
SQLite ADD history for a memory absent from the primary vector store.
[PY-ADD-PERSIST]

**Documented.** Message saving occurs after vector, history, and entity work. A
SQLite message-save failure can raise after earlier stores changed. Entity
linking failures are generally swallowed and do not fail the add. [PY-ADD-PERSIST]

### Prompt linking versus persisted linking

**Documented.** The prompt asks for optional `linked_memory_ids` and describes
existing IDs as UUID strings. The runtime instead maps retrieved UUIDs to
sequential strings such as `"0"`, creates a `uuid_mapping`, and sends only those
sequential IDs to the LLM. Neither Python nor TypeScript reads the extracted
`linked_memory_ids` field after parsing, and neither uses its UUID mapping.
[PY-PROMPT] [PY-PROMPT-OUTPUT] [PY-ADD-PERSIST] [TS-ADD]

**Documented.** Runtime entity links come from a separate NLP pass over each new
memory. Python uses spaCy candidates when the optional model loads; TypeScript
uses `compromise` when available and regex heuristics otherwise. Entity records
are exact-text or high-similarity upserts whose payload holds linked live-memory
IDs. [PY-ENTITY-EXTRACT] [PY-SPACY] [TS-ENTITY-EXTRACT] [PY-ENTITY-WRITE]

**Inference.** Prompt-declared narrative links, contradictions, and preference
updates are currently discarded in OSS. The entity index can connect shared
surface entities, but it cannot be assumed to preserve the LLM's relation intent
or a typed graph edge.

### Add without inference

**Documented.** With `infer=False`, Python skips system messages and stores every
other message separately, preserving role and optional message `name` as
`actor_id`. Each row is embedded, inserted, and then written to history. It does
not execute the inferred batch's rolling-message save or entity-linking phase.
[PY-ADD]

**Documented.** TypeScript similarly stores each non-system message directly,
but does not preserve role/actor in the shown result/payload path and returns the
ADD event nested in result metadata. [TS-ADD]

**Inference.** `infer=False` is not merely a deterministic version of inferred
add. It creates a different payload/projection footprint and can therefore
produce different search behavior for the same text.

### Python async and TypeScript async differences

**Documented.** Python `AsyncMemory` largely mirrors sync behavior by running
the same synchronous provider methods through `asyncio.to_thread`. It is an
awaitable facade, not proof that each adapter has native asynchronous I/O. It
uses bounded concurrency for entity searches and concurrent deletion within
`delete_all`. [PY-ASYNC-ADD] [PY-ASYNC-SEARCH] [PY-ASYNC-MUTATE]

**Documented.** TypeScript OSS is Promise-based throughout. Its write, search,
history, entity, and reset sequences are structurally similar but use different
payload casing, entity extraction, provider implementations, and history schema.
[TS-ADD] [TS-SEARCH] [TS-MUTATE]

**Documented divergence.** Python sync `delete_all` deletes sequentially and
stops on the first propagated delete failure. Python async gathers a batch with
`return_exceptions=True`, logs per-memory failures, clears the entire scoped
entity collection, and still returns a success message. [PY-DELETE-ALL]
[PY-ASYNC-MUTATE]

**Inference.** In async `delete_all`, failed primary-memory deletions can survive
while all entity rows for the scope are removed. The success response does not
report partial deletion.

**Documented hosted-client caveat.** `AsyncMemoryClient.__init__` creates an
`httpx.AsyncClient` but validates the API key through synchronous `requests.get`
inside the constructor. Construction can therefore block an event-loop thread
before any awaited method runs. [HOSTED-ASYNC]

### Search

**Documented trace.** [PY-SEARCH] [PY-SCORING]

```text
search(query, filters containing user_id/agent_id/run_id, top_k=20,
       threshold=0.1, rerank=False, explain=False)
  -> reject reference_date and top-level scope arguments
  -> validate/trim query, scope IDs, threshold, and top_k
  -> translate generic advanced filters into adapter-facing forms
  -> lemmatize query and heuristically extract up to 8 unique entities
  -> embed query
  -> semantic vector search with max(top_k * 4, 60)
  -> optional adapter keyword search with the same over-fetch
  -> optional entity-collection searches, up to 500 hits per entity
  -> discard expired semantic candidates unless show_expired=True
  -> reject candidates below threshold on semantic score alone
  -> additive fusion of semantic, normalized BM25, and entity boost
  -> sort and truncate to top_k
  -> optionally rerank; on reranker failure retain fused order
  -> return result payloads and optional score_details
```

**Documented.** Candidate membership comes only from semantic results. Keyword
results contribute BM25 scores by memory ID, and entity results contribute
boosts by linked memory ID, but neither adds a new candidate absent from the
semantic over-fetch pool. The threshold is applied to semantic score before
fusion. [PY-SEARCH] [PY-SCORING]

**Inference.** This is semantic candidate generation with additive reranking,
not a union-based hybrid retriever. A lexical-only match outside the semantic
pool cannot be rescued by BM25, and a low semantic score cannot be rescued by a
strong keyword or entity score.

**Documented.** The fusion denominator depends on whether any BM25 and entity
scores exist in the whole result set: `1.0` for semantic, plus `1.0` if BM25 is
active and `0.5` if entity boost is active. `explain=True` returns the individual
signals and denominator. [PY-SCORING]

**Inference.** Scores are rank features, not probabilities or truth confidence.
The same semantic score can produce a different final score when another result
activates an additional signal.

**Documented.** Expiry is filtered after bounded over-fetch. `search` and
`get_all` can return fewer than `top_k` even when additional non-expired records
exist beyond the `max(top_k * 4, 60)` fetch window. [PY-GET-SEARCH]

### Get, list, and history

**Documented.** `get(memory_id)` reads by unscoped ID and returns expired records;
it does not accept scope filters or `show_expired`. `get_all` requires at least
one scope field and filters expired rows by default. `history(memory_id)` is also
an unscoped ID lookup. [PY-GET] [PY-GET-SEARCH] [PY-HISTORY]

**Documented.** TypeScript `getAll` likewise requires a snake_case scope filter,
over-fetches before expiry filtering, and can underfill `topK`; its explicit
update and delete paths preserve the same vector-then-history-then-entity order.
[TS-GET-MUTATE]

**Documented.** The self-hosted server exposes the same ID-only get, update,
history, and delete operations. Its admin no-filter `GET /memories` bypasses the
SDK listing path and intentionally returns a raw list without expiry filtering.
[SERVER-ENDPOINTS]

**Inference.** Expiration is retrieval visibility, not deletion, access denial,
or history redaction. Anyone authorized by the enclosing application who knows
a memory ID can still retrieve it through the OSS `get` surface.

### Explicit update

**Documented trace.** [PY-MUTATE] [PY-MUTATE-INTERNAL]

```text
update(memory_id, text and/or metadata and/or expiration_date)
  -> embed new text before reading the current record when text is supplied
  -> read primary vector record by ID
  -> preserve original created_at and immutable scope/actor identity fields
  -> merge permitted metadata; recompute MD5 and lemmatized text
  -> re-embed unchanged text too when the update is metadata/expiry-only
  -> update primary vector and payload
  -> append SQLite UPDATE history
  -> if text changed, best-effort remove old entity links and add new links
  -> return a generic success message
```

**Documented.** Inferred add never invokes this operation. Update is a separate
caller-directed mutation API. Identity keys in update metadata are stripped,
but other metadata is merged into the stored payload. [PY-MUTATE]
[PY-MUTATE-INTERNAL]

**Inference.** If vector update succeeds and history append fails, live content
changes while the operation raises and history remains stale. If entity cleanup
fails, search boosts can reference old entities or omit new ones without failing
the update.

### Delete, delete-all, and reset

**Documented trace.** [PY-MUTATE] [PY-MUTATE-INTERNAL] [PY-DELETE-ALL]
[PY-RESET]

```text
delete(memory_id)
  -> read vector payload by ID
  -> delete primary vector
  -> append DELETE history with old text and is_deleted=1
  -> best-effort remove memory ID from entity rows

delete_all(scope IDs)
  -> require at least one caller-selected scope filter
  -> repeatedly list batches of 1000
  -> stop on empty batch or repeated batch signature
  -> call per-memory delete
  -> return a generic success message

reset()
  -> destructively reset all history/messages and vector collections
  -> recreate clients/stores
  -> reset entity collection if it was initialized in this process
```

**Inference.** Deleting the primary vector before appending history creates a
failure window where data is gone but no deletion event exists. Because entity
cleanup follows history, a history failure also leaves dangling entity links.

**Documented.** Reset ordering differs. Python sync resets SQLite before the
primary vector store. Python async deletes the primary vector collection before
resetting SQLite. TypeScript resets history first, catches and logs primary
collection deletion errors, and can finish reset while underlying vectors remain;
the LangChain adapter is explicitly skipped. [PY-RESET] [PY-ASYNC-MUTATE]
[TS-MUTATE]

**Inference.** Reset is not an atomic erasure guarantee. A process crash or
adapter failure can preserve one of history, vectors, or entities, and the exact
survivor depends on runtime and provider.

## Filtering is not authorization

**Documented.** Python requires one or more of `user_id`, `agent_id`, or `run_id`
for add/search/get-all/delete-all. It strips those keys and `actor_id` from
caller metadata, then writes scope only from explicit parameters. This prevents
freeform metadata from silently changing a record's scope. [PY-SCOPE]
[PY-SCOPE-STORE]

**Documented.** The in-process OSS classes have no principal, role, capability,
tenant-membership, policy version, or authorization callback. Any caller holding
the object can select any scope string and can get, update, delete, or inspect
history by memory ID. [PY-SCOPE] [PY-GET] [PY-MUTATE]

**Documented.** The self-hosted server authenticates Bearer JWTs, per-user API
keys, a legacy admin key, or an explicit `AUTH_DISABLED` mode. JWT/API-key lookup
resolves an application `User`; admin-only dependencies protect configuration,
bulk deletion, and reset. [SERVER-AUTH] [SERVER-ENDPOINTS]

**Documented.** Ordinary create, scoped list, ID get, search, update, history,
and single delete depend only on `verify_auth`. Their handlers pass caller
scope IDs or memory IDs directly to the shared `Memory` instance without binding
them to the authenticated user's database ID. API-key ownership is enforced for
key management, but there is no corresponding ownership relation in the memory
payload schema. [SERVER-AUTH] [SERVER-ENDPOINTS] [SERVER-KEYS] [SERVER-MODELS]

**Inference.** In the self-hosted server, an authenticated non-admin user can
request another application's scope if they can name it, and can read or mutate
an arbitrary memory by ID. `user_id`, `agent_id`, and `run_id` are organization
and filtering fields, not access-control boundaries. Calling them tenant IDs
would be unsafe without an enclosing authorization layer.

**Documented.** Setting `AUTH_DISABLED=true` treats callers as admin for protected
admin dependencies. Auth rate limits are present on register/login/refresh, but
the inspected memory endpoints have no limiter decorators. [SERVER-AUTH]
[SERVER-AUTH-ROUTES] [SERVER-RATE]

## Filter and adapter portability

**Documented.** The common filter layer accepts exact values, wildcard, range,
membership, contains/icontains, and AND/OR/NOT forms, then passes translated
structures to the selected adapter. The public vector-store base contract does
not define a filter grammar or capability negotiation. [PY-GET-SEARCH]
[PY-FILTERS] [PY-VECTOR-BASE]

**Documented examples of divergence.** Chroma drops wildcard clauses and maps
contains/icontains or unknown positive operators to equality. FAISS implements
only direct equality or list membership in the inspected filter helper.
Weaviate's search and keyword-search paths apply only the three scope fields,
ignoring other metadata filters. [ADAPTER-CHROMA] [ADAPTER-FAISS]
[ADAPTER-WEAVIATE]

**Inference.** Input validation proves only that Mem0 recognizes an operator,
not that the configured backend enforces the intended predicate. Authorization
must never depend on this portability layer.

**Documented.** The Python config names 25 vector providers. Keyword search is
optional in the base contract and returns `None` by default. Qdrant needs a BM25
sparse slot and `fastembed`; an existing pre-v3 collection remains semantic-only
and requires a fresh collection to enable that slot. PostgreSQL keyword search
reads `payload->>'text_lemmatized'` and returns `None` on failure. [PY-VECTORS]
[PY-VECTOR-BASE] [ADAPTER-QDRANT] [ADAPTER-PGVECTOR]

**Inference.** "Hybrid search" is a capability-dependent mode rather than a
portable invariant. Store selection, optional packages, pre-existing schema,
payload casing, and adapter errors can silently reduce it to semantic ranking.

## Entity and graph behavior

**Documented.** External graph-store configuration was removed from OSS. The
remaining OSS entity collection is used to boost ranking and is not exposed as
a queryable relation graph or `relations` field. Managed Platform documentation
claims a separate always-on native graph. [MIGRATION] [PLATFORM-DIFF]

**Documented.** Python entity extraction can emit `PROPER`, `QUOTED`, `TOPIC`,
and `IDENTIFIER` candidates. If spaCy or its English model cannot load, extraction
returns no entities and lemmatization falls back to original text. The loader may
attempt to download `en_core_web_sm` at runtime before marking the load failed.
[PY-ENTITY-EXTRACT] [PY-SPACY] [PY-LEMMA]

**Documented.** Entity upsert checks exact normalized text first, then accepts a
top semantic match at score `>= 0.95`. Search extracts at most eight entities,
queries up to 500 entity rows per entity, accepts matches at `>= 0.5`, and reduces
boost for entities linked to many memories. [PY-INIT] [PY-ENTITY-BOOST]

**Inference.** Entity identity is heuristic and model/adapter dependent. Similar
surface strings may merge, one conceptual entity may split, and broad entities
can create fan-out. The collection is useful as a ranking projection but lacks
the typed edge semantics, provenance, temporal validity, and reconciliation
needed for a canonical knowledge graph.

## Expiration and temporal behavior

**Documented.** `expiration_date` is normalized to `YYYY-MM-DD`. A record is
expired only when its date is strictly before the current UTC date, so it remains
visible through its named date. Invalid values already present in a payload are
treated as non-expiring. [PY-EXPIRY] [TS-EXPIRY]

**Documented.** Expiration only changes default `search` and `get_all` visibility.
There is no background TTL deletion, purge, entity cleanup, or history cleanup.
`show_expired` restores visibility. ID get and history do not hide expired rows.
[PY-GET-SEARCH] [PY-GET] [PY-HISTORY]

**Documented.** OSS rejects the temporal `timestamp` parameter on add and
`reference_date` on search. Because add does not pass a timestamp to the prompt
builder, observation date defaults to the current UTC date. [PY-ADD]
[PY-PROMPT-BUILDER]

**Inference.** A historical transcript imported today can have relative phrases
resolved against today by the LLM. `expiration_date` must not be confused with
event time, valid time, capture time, retention enforcement, or secure erasure.

## Telemetry and external data movement

### OSS library telemetry

**Documented.** Python and TypeScript telemetry is enabled by default and can be
disabled with `MEM0_TELEMETRY=false`. Hot-path events default to 10 percent
sampling, while lifecycle/reset/notice events bypass sampling. Both send to a
hard-coded PostHog project at `us.i.posthog.com`. [PY-TELEMETRY] [TS-TELEMETRY]

**Documented.** Python OSS events include package/runtime/OS details, collection,
vector size, selected provider class names, function/version, filter-key names,
and unsalted MD5 encodings of user/agent/run IDs. Hosted-client telemetry is not
sampled and can use the account email returned by `/v1/ping/` as its PostHog
distinct ID. [PY-TELEMETRY] [PY-TELEMETRY-EVENTS]
[PY-TELEMETRY-FILTERS] [HOSTED-CLIENT]

**Documented.** Notice logic remotely evaluates a PostHog feature flag, receives
notice copy/configuration, can print that copy to stderr, and sends a notice event
including the payload. [PY-NOTICES]

**Inference.** The inspected ordinary memory events do not intentionally attach
message or memory text, but scope hashes are stable pseudonymous identifiers and
low-entropy IDs may be guessable. Provider/collection metadata and remote feature
flag evaluation still constitute external telemetry and control-plane contact.

### Self-hosted server telemetry and request logs

**Documented.** Server telemetry is also enabled by default. It sends at most an
`admin_registered` and `onboarding_completed` event per persisted install state,
including install UUID, email domain, server version, and, for onboarding, the
operator's freeform use-case text. [SERVER-TELEMETRY]

**Documented.** Server request logs persist method, path, status, latency,
authentication type, and creation time. The schema does not include body, query
parameters, principal ID, or memory ID as a separate field, although a path may
contain a memory ID. [SERVER-REQUEST-LOG] [SERVER-MODELS]

### Model, embedding, vector, and reranker egress

**Documented.** "Self-hosted" does not imply all-local processing. Python defaults
to OpenAI for both LLM and embeddings; the default base URLs are OpenAI endpoints.
The full source conversation, rolling context, and retrieved existing-memory text
are sent to the configured extraction LLM; memory/query/entity text is sent to
the configured embedder; an optional remote reranker can receive query and
candidate text. [PY-CONFIG] [OPENAI-LLM] [OPENAI-EMBED] [PY-ADD-PERSIST]

**Inference.** A privacy assessment must cover every configured provider and
telemetry channel. Running the FastAPI server on owned infrastructure does not,
by itself, contain user content.

## Failure, drift, and concurrency analysis

| Stage                        | Documented behavior                                                                                        | Inferred residual state after failure                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Inferred vector batch insert | Retry individually; log failed rows; continue with all prepared records [PY-ADD-PERSIST]                   | Returned/history-only phantom memories are possible.                            |
| History batch append         | Retry individually; log failures; continue [PY-ADD-PERSIST]                                                | Live vectors can lack ADD history.                                              |
| Entity linking               | Broadly caught and logged [PY-ENTITY-WRITE]                                                                | Live vectors can lack entity projection or retain stale links.                  |
| Final message save           | Runs after all stores and may raise [PY-ADD-PERSIST]                                                       | Caller may retry an add that already partially committed, creating duplicates.  |
| Update                       | Vector first, history second, entity repair third [PY-MUTATE-INTERNAL]                                     | Live content, history, and entity links can represent three different versions. |
| Delete                       | Vector first, history second, entity cleanup third [PY-MUTATE-INTERNAL]                                    | Missing vector with no tombstone history and dangling entity links is possible. |
| Async delete-all             | Suppresses per-row exceptions, then clears scoped entities and returns success [PY-DELETE-ALL]             | Surviving memories can lose all entity projection.                              |
| Reset                        | Runtime-specific destructive order; some adapter errors swallowed [PY-RESET] [PY-ASYNC-MUTATE] [TS-MUTATE] | Erasure completeness cannot be inferred from a success response alone.          |

**Documented.** Python SQLite uses `check_same_thread=False` with one in-process
`threading.Lock`, and each history/message operation has its own SQLite
transaction. The lock does not encompass vector or entity operations. [PY-SQLITE]
[PY-SQLITE-OPS]

**Inference.** The lock serializes calls through one manager instance only. It
does not provide distributed exclusion, a unique hash constraint, compare-and-set
entity updates, or a transaction across multiple Mem0 processes.

**Inference.** Search-before-insert dedup and read-modify-write entity upserts
have race windows. Two writers can add duplicate exact memories or overwrite
each other's linked-ID changes, depending on adapter semantics.

**Documented.** Hosted clients set a 300-second HTTP timeout and translate HTTP
and network exceptions into structured errors. The inspected decorator records
`Retry-After` metadata for 429 responses but does not perform retries. [HOSTED-CLIENT]
[HOSTED-ERRORS]

**Unknown.** Retry, idempotency, and transaction behavior inside the managed
service are not reconstructible from these clients.

## Migration and compatibility

**Documented.** The OSS v2-to-v3 guide declares breaking API/default changes,
ADD-only extraction, graph removal, and per-language naming changes. It advises
fresh Qdrant collections for BM25 capability but does not define a cross-provider
atomic data migration or rollback protocol. [MIGRATION] [ADAPTER-QDRANT]

**Documented.** Python SQLite automatically compares the existing `history`
columns with its expected ten-column schema. On mismatch it renames the table,
creates the new schema, copies only intersecting columns, drops the old table,
and commits in one SQLite transaction. [PY-SQLITE]

**Inference.** That migration preserves common columns but intentionally discards
legacy-only columns. It is a history-table migration, not a vector-payload,
entity-index, embedding-model, or collection-version migration.

**Documented.** TypeScript default SQLite executes `CREATE TABLE IF NOT EXISTS`
for `memory_history` and `messages`; the inspected manager has no analogous
column-shape migration. [TS-SQLITE]

**Inference.** An existing TypeScript table with the same name but incompatible
columns can survive initialization and fail only when prepared statements run.

**Documented.** The server's Alembic chain creates authentication, API-key,
request-log, settings, single-admin, refresh-token, and request-log index schema.
The pgvector memory table remains adapter-managed, and SQLite history is a mounted
file outside those Alembic transactions. [SERVER-ALEMBIC-AUTH]
[SERVER-ALEMBIC-LOGS] [SERVER-ALEMBIC-SETTINGS] [SERVER-ALEMBIC-ADMIN]
[SERVER-ALEMBIC-REFRESH] [SERVER-ALEMBIC-BRIN] [SERVER-DOCKER]

**Unknown.** Safe in-place migration behavior across all 25 vector providers,
embedding-dimension changes, payload casing changes, partially populated entity
collections, and every historical Mem0 release was not established.

## Benchmark assessment

**Vendor/author claim.** The migration guide attributes a roughly halved

**Unknown.** The pinned checkout does not contain the claimed evaluation code,

**Inference.** No benchmark number in this dossier establishes correctness,
security, durability, filter parity, deletion completeness, or fitness for
Curiosity. Top-200 benchmark retrieval also differs materially from the OSS
default `top_k=20`.

## Saturation stop

The investigation stopped after the Python sync and async paths, TypeScript OSS,
self-hosted server, hosted clients, storage schemas, migrations, representative
adapters, telemetry, prompts, tests, and benchmark documentation converged on the
same core model. Later searches repeated already established call sequences and
adapter caveats rather than falsifying them. Further progress would require a
new evidence class: controlled runtime fault injection, a full adapter matrix,
the separate benchmark repository and artifacts, or access to managed Platform
internals. Those activities are outside this clean-room scope.
