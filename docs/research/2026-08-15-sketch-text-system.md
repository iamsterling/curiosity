# Sketch dynamic text system — evidence study

**Decision served:** establish what Sketch is demonstrably doing with dynamic text, and what is *not* safe to infer, before any separate Crafty text decision.
**Scope:** published Sketch file-format/API/product documentation and Apple primary documentation only; no application probing, decompilation, or source copying.
**Research date / access date:** 2026-08-15. **Status:** complete for the public-evidence frame.

**Schema-evidence pin (review remediation):** all Sketch schema and changelog findings below were re-inspected on 2026-08-15 at official `sketch-hq/sketch-document` commit [`4493900abbfa49ae82fbcb8ad85cccf2cc2256b0`](https://github.com/sketch-hq/sketch-document/commit/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0) (commit timestamp 2023-04-03). That commit's `packages/file-format/package.json` declares [`@sketch-hq/sketch-file-format` 6.5.0](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/package.json). Every schema/changelog citation is commit-addressed; current Sketch product documentation remains separately dated current-product evidence.

## Executive summary

1. **Confirmed fact — Sketch persists rich text as a string plus ranged attributes, not as a flattened outline.** A text layer has an `attributedString`; each range records a location and length and can carry a font descriptor, colour, kerning, paragraph style, and vertical alignment. The public schema also persists text behaviour, line-spacing behaviour, and `glyphBounds`. [Sketch file-format text schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/layers/text.schema.yaml), [attributed-string schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/attributed-string.schema.yaml), [string-attribute schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/string-attribute.schema.yaml) **Confidence: confirmed fact.**
2. **Confirmed fact — its publicly exposed model covers real typography rather than a single font property:** font name/size/variation, character spacing, explicit or automatic line height, paragraph spacing/alignment, decorations, baseline choice, text transform, lists, ligature/kern/baseline controls, OpenType features, and variable-font axes. Some of those are exposed in the current Mac UI; the narrower persisted schema is the interoperability floor, not a statement of all internal state. [Sketch Text, 2026-06-22](https://www.sketch.com/docs/designing/text/), [Sketch JavaScript API](https://developer.sketch.com/reference/api/llms-full.txt), [font-descriptor schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/font-descriptor.schema.yaml) **Confidence: confirmed fact.**
3. **Confirmed fact — text sizing is a first-class layout dependency.** Current UI offers Fit, Fixed, and Relative sizing independently for width/height; Fixed wraps. The historical file format calls its modes Flexible, Fixed, and FixedWidthAndHeight. This is an evolution/terminology distinction, not evidence that the present UI maps one-to-one to old enum values. [Sketch Text](https://www.sketch.com/docs/designing/text/), [text-behaviour schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/enums/text-behaviour.schema.yaml) **Confidence: confirmed fact (facts); unknown (exact mapping).**
4. **Confirmed fact — fonts are a document portability concern, not merely a local renderer choice.** Documents can contain font references/data; Sketch exposes missing-font replacement, PDF preview when a font is missing, non-editability until replacement/change, and embeds most non-system OpenType/TrueType fonts subject to licence. Variable custom settings can themselves cause a missing-font state, and static/variable or version duplicates are documented hazards. [Sketch Fonts, 2026-04-07](https://www.sketch.com/docs/interface-and-settings/document-settings/fonts/), [abstract-document schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/abstract-document.schema.yaml), [font-reference schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/font-ref.schema.yaml), [data-reference schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/data-ref.schema.yaml) **Confidence: confirmed fact.**
5. **Boundary finding — no reviewed Sketch primary source establishes whether the Mac app uses Core Text, TextKit 1/2, `NSTextView`, or a custom shaper/layout engine.** The `attributedString` and `fontDescriptor` vocabulary resembles Apple APIs but is insufficient proof of a runtime dependency. Apple documents that its text stack can supply kerning, ligatures, line breaking and justification, and that Cocoa text input can support composition; that only describes available macOS facilities, not Sketch’s architecture. [Apple, *Text Programming Guide for iOS* (archived, 2018)](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/TextAndWebiPhoneOS/Introduction/Introduction.html), [Apple, *Typographical Concepts* (archived, 2018)](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/TextAndWebiPhoneOS/TypoFeatures/TextSystemFeatures.html) **Confidence: confirmed absence within reviewed evidence; runtime conclusion unknown.**

**Competitor-specific verdict:** **adapt concepts, not an implementation.** Sketch is strong evidence that a durable text document needs attributed runs, explicit sizing/layout modes, font identity/availability state, and component-safe text overrides. Its undocumented native layout/rendering path is **rejected as a transferable claim**. This is a research verdict, not a Crafty design decision.

Exact merge/conflict semantics are unknown. |

### 2. Layout, shaping, Unicode, measurement, and line modes

**What is documented.** Sketch’s current text UI exposes character spacing, line height, paragraph spacing, horizontal and vertical alignment, lists, kern/ligature/baseline menu options, OpenType feature selection, text-on-path, and Fit/Fixed/Relative dimensions. Its text docs say a newly created layer’s line height automatically follows font size; changing line height/typeface/size keeps the first baseline in place, and changing typeface/weight in a paragraph keeps line height consistent. [Sketch Text](https://www.sketch.com/docs/designing/text/) **Confidence: confirmed fact.**

The public API confirms automatic line height is represented as `null` and exposes `getDefaultLineHeight()`. It documents `fontWeight` fallback to the closest available weight, `system` as OS family, style/stretch/small-caps traits, and variable axes constrained by a recognised font’s min/max range. [Sketch JavaScript API](https://developer.sketch.com/reference/api/llms-full.txt) **Confidence: confirmed fact.**

The format enum documents older `textBehaviour` values as Flexible, Fixed, and FixedWidthAndHeight; its fixed-line-height enum has None, Legacy, and Consistent baseline. [Text-behaviour schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/enums/text-behaviour.schema.yaml), [line-spacing-behaviour schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/enums/line-spacing-behaviour.schema.yaml) **Confidence: confirmed fact.** The *meaning* of legacy vs consistent-baseline processing is not described, so it cannot establish a layout algorithm. **Verdict: defer interpretation.**

**What this does and does not show about shaping.** Apple explains why a layout engine must map non-1:1 character/glyph relationships (combining marks and ligatures), perform contextual selection, direction-sensitive layout, and line breaking; it also says Unicode carries bidi/contextual/line-break information. [Apple, *Typographical Concepts*](https://developer.apple.com/library/archive/documentation/StringsTextFonts/Conceptual/TextAndWebiPhoneOS/TypoFeatures/TextSystemFeatures.html) **Confidence: confirmed fact about Apple’s text model.** Sketch’s exposed ligature control, font fallback/replacement and glyph-bounds persistence are **highly credible inference** that Sketch must account for shaped glyph results rather than one glyph per stored character, but do not identify the shaping engine, Unicode version, segmentation rules, shaping cache, fallback order, hyphenation, justification, truncation algorithm, writing-mode support, or bidi implementation. **Verdict: reject stronger architectural attribution.**

**Measurement.** Sketch says the Mac app measures layers—including text—in macOS points, with one point equalling one Canvas pixel by default. [Sketch Text](https://www.sketch.com/docs/designing/text/) **Confidence: confirmed fact.** It persists `glyphBounds`, but the schema does not specify its coordinate system, lifecycle, relationship to bounds/line boxes, or whether it is authoritative versus cache/derived data. **Verdict: treat it as an interchange field, not a measurement algorithm.**

### 5. Components/symbols, shared styles, and resizing

Sketch symbol instances persist a `symbolID`, scale and `overrideValues`; an override names a target and stores a string/UUID/file/data value. [Symbol-instance schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/layers/symbol-instance.schema.yaml), [override-value schema](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/schema/objects/override-value.schema.yaml) **Confidence: confirmed fact.** Its API documents text overrides for `stringValue`, text-style ID, size, colour, decoration, and horizontal alignment, with path-based nested-symbol addresses. [Sketch JavaScript API — Symbol Override](https://developer.sketch.com/reference/api/llms-full.txt) **Confidence: confirmed fact.**

The current docs say text layers can be Fit, Fixed or Relative; Fixed wraps. Stack docs say text is the exception that can be Fit as a stack item, while other items are fixed/fill, and Fit stacks resize around content. [Sketch Text](https://www.sketch.com/docs/designing/text/), [Sketch Stack Layout](https://www.sketch.com/docs/designing/stack-layout/) **Confidence: confirmed fact.**

**Verdict — adapted lesson:** text content, text-style and dimension-related changes must be resolvable in the component/layout context, rather than assuming a fixed pre-expanded copy. **Risk/unknown:** the public sources do not specify override precedence against local rich-text runs, propagation/reflow scheduling, source/instance sync behaviour for `dontSynchroniseWithSymbol`, or exact symbol resizing equations.

### 6. File format and interchange evolution

Sketch documents have been ZIP archives of JSON plus binary assets since Sketch 43. `document.json` holds shared document data, individual page JSON holds page content, and `user.json` holds viewport/zoom and UI metadata. The published specification is versioned separately from the app and is intended for validation/code generation. [Sketch File format](https://developer.sketch.com/file-format/), [Sketch Specification](https://developer.sketch.com/file-format/spec) **Confidence: confirmed fact.**

The format has sequential document and compatibility versions. Sketch warns that saving a newer document through an older compatible Sketch loses data only understood by the newer version. [Sketch Versioning](https://developer.sketch.com/file-format/versioning) **Confidence: confirmed fact.** The pinned package changelog records text-relevant schema-package history: its 3.4.3 entry says it added a missing text-behaviour enum; 3.5.0 adds document model version 126 and embedded fonts; 3.7.0 adds `missingLibraryFontAcknowledged` and version 135; and 6.2.0 adds `strikethroughStyle`. It does not establish the first app/runtime introduction of any behaviour. [File-format changelog](https://raw.githubusercontent.com/sketch-hq/sketch-document/4493900abbfa49ae82fbcb8ad85cccf2cc2256b0/packages/file-format/CHANGELOG.md) **Confidence: confirmed fact about package changelog entries; unknown for app-runtime chronology.**

**Current vs historical caution:** current product documentation is dated 2026, whereas published format wording and enum naming preserve older representation. Schema history establishes that fields changed; it does not establish a current runtime algorithm or a backwards-compatible semantic mapping. **Verdict: use the schema as interchange evidence only.**

**Ghost features / market-wide limitation finding:** the public contract is rich enough to demonstrate dynamic typography, yet omits the correctness-critical implementation contracts: offset encoding, Unicode/bidi policy, fallback ordering, exact derived-metrics semantics, and IME behaviour. The omission is not evidence Sketch lacks these; it is evidence they cannot safely be copied or relied on for interoperable reimplementation. **Verdict: treat them as independent requirements, not inherited competitor behaviour.**

## Gaps, contradictions, and risks

1. **No runtime-framework evidence.** “Mac app” and Apple-like type names do not prove use of Cocoa/Core Text/TextKit. This is the largest false-certainty risk. **Unknown.**
2. **No sample-document differential test was authorised.** Therefore `glyphBounds`, variation keys, `textBehaviour`, line-spacing legacy mode, and override precedence have schema-level but not behavioural confirmation. **Unknown.**
3. **Range indexing is undocumented.** This is particularly material for emoji, combining marks and non-BMP characters. **Unknown.**
4. **Current UI vs historical schema is only partly triangulated.** “Fit/Fixed/Relative” differs from “Flexible/Fixed/FixedWidthAndHeight”; no official mapping was located. **Contradiction/terminology drift recorded; no resolution asserted.**
5. **Font embedding has a legal and operational edge.** Sketch’s own docs make user licensing a precondition and document variable/static and version duplication. An embedded byte payload does not establish a transferable licence or identical local font resolution. **Confirmed risk.**
6. **No benchmark claim.** The sole performance statement is vendor qualitative guidance that outlining lots of text can slow Sketch; it must not be compared numerically with another renderer. **Confirmed methodology caveat.**

## Recommendations (research verdicts only)

| Recommendation | Confidence | Rationale / verdict |
|---|---|---|
| Preserve the distinction between authored characters/attributes and resolved glyph geometry in any later decision. | Highly credible inference | Sketch’s public format has both attributed content and `glyphBounds`, and its UI’s baseline behaviour makes layout derived. **Adapted.** |
| Treat font availability, explicit replacement and embedding permissions as document/interchange state, not a best-effort rendering fallback. | Confirmed fact | Directly documented by Sketch. **Adapted.** |
| Require an explicit specification/test decision for range units, bidi/IME, fallback ordering, and derived-layout cache invalidation. | Highly credible inference | Sketch’s public sources leave all four ambiguous; they are correctness boundaries. **Deferred pending a separate decision.** |
| Do not use Sketch to select a native Apple text API, a shaping engine, cache design, atlas policy, or numeric performance target. | Confirmed absence in reviewed sources | No direct public Sketch evidence; Apple capability docs do not bridge the gap. **Rejected.** |
| Use component text override evidence only for the problem: instance text needs target-addressed sparse overrides and layout-aware resolution. | Confirmed fact / inference boundary stated | Exact merge and reflow semantics are unknown. **Adapted, bounded.** |

## Audit trail and source quality

### Research loop

1. **Pass 1 — schema/format:** read Sketch’s official format overview/spec/versioning, current `sketch-document` schema and changelog. Established the persisted text, fonts, symbol and version fields.
2. **Synthesis:** public model is structurally rich but says little about runtime layout.
3. **Curiosity pass (scored relevance × value × novelty − cost):** (a) Cocoa/TextKit dependency (high relevance, high value, low evidence likelihood); (b) variable/embedded-font portability (high/high); (c) exact UI-vs-schema sizing mapping (high/high); (d) IME/bidi and caching (high relevance, low public-evidence likelihood); (e) static source/probing (off-frame/forbidden). Pursued a–d at reduced breadth.
4. **Pass 2 — product/API:** read current Text/Fonts/Stack docs and developer API. Confirmed UI behaviour, font hazards, axes, text override vocabulary, and Stack interaction.
5. **Pass 3 — dependency falsification:** read Apple primary text material. It establishes platform capabilities but no Sketch linkage; recorded absence rather than inferring it.
6. **Stop check:** all seven sub-questions have evidence or an explicit unknown; new source attempts were adding detail rather than distinct claims. The multi-source sources agree on public format/product boundaries. **Stopped for coverage and saturation.**
